# Summary

We introduce an opt-in, queue-level mechanism that allows a Queue to perform **eInvoicing** and **eReporting** steps as part of receipt processing.
The mechanism mirrors the existing SCU pattern: like the SCU, eInvoicing and eReporting are separate components behind an interface that receive the `ReceiptRequest`/`ReceiptResponse` pair and return a (potentially modified) `ReceiptResponse`.
The sequence of calls within receipt processing is fixed: **1. SCU (fiscalization), 2. eInvoicing, 3. eReporting**. Each step receives the response **including all fields generated by the Queue and the preceding steps** — so eInvoicing sees everything the SCU produced, and eReporting sees everything the SCU and eInvoicing produced. The eInvoicing and eReporting services are called **strictly via HTTP** against an endpoint configured on queue level.

# Motivation

Fiscal regulation across our markets is expanding from *fiscalization of the single receipt* towards *transmission of invoices and transactional data to authorities and business recipients*:

- **eInvoicing**: creating structured invoices in a mandated format (e.g. PEPPOL BIS, Factur-X, national formats). The transmission of such invoices to the recipient (eDelivery) is a separate concern and not covered by this RFC.
- **eReporting**: transmitting transactional data to a tax authority *beyond* the fiscalization itself (e.g. digital reporting requirements such as ViDA).

These obligations are distinct from CTC (continuous transaction control) fiscalization: where the middleware already transmits data to an authority today (GR myDATA, ES VeriFactu), that transmission *is* the fiscalization — it creates the fiscal proof for the receipt and therefore correctly lives in the SCU. eInvoicing and eReporting as defined here are *additional* obligations on top of the fiscalized receipt, and the v2 middleware has no place for them today:

- PosCreators who need eInvoicing or eReporting on top of fiscalization have no integration point in the middleware and must build it themselves — losing the queue-generated fields (`ftQueueItemID`, `ftReceiptIdentification`, SCU signatures, QR codes) that the invoice or report must reference.
- New mandates (and markets without an SCU-style fiscalization at all) would each force another ad-hoc solution.

The expected outcome is a single, market-agnostic extension point in the shared localization: a Queue can be configured to call one eInvoicing and/or one eReporting service after fiscalization, and the services can enrich the `ReceiptResponse` with additional signatures, state, and state data — exactly the way PosCreators already understand SCU behavior today.

# Guide-level explanation

## New concepts

- **eInvoicing service**: an HTTP service that receives the fully fiscalized receipt (`ReceiptRequest` + `ReceiptResponse`) and creates a structured invoice. It typically returns additional signatures (e.g. a document id, a validation URL, or a QR code pointing to the invoice).
- **eReporting service**: an HTTP service with the same contract that transmits transactional data to an authority.
- **Post-fiscalization processing**: the new step in the queue's sign pipeline where these services are called — after the country-specific processing (including the SCU call) has completed, and before the response is persisted and returned to the POS.

Both services are **opt-in**. A queue that doesn't configure them behaves exactly as today.

### Synchronous vs. asynchronous reporting

Reporting obligations come in two fundamentally different flavors, and this RFC only covers one of them:

- **Synchronous reporting** is bound to a single receipt: it runs while the receipt is processed, and its results (signatures, state data) are embedded in the `ReceiptResponse` handed back to the POS. This is what the mechanism in this RFC provides — the middleware calls the eReporting service inside the sign pipeline and waits for the result.
- **Asynchronous reporting** is bound to a schedule, not to a single receipt: batch/periodic obligations (e.g. SAF-T-style exports or monthly submissions) that run at configured times over already-processed data. This is *not* covered by the per-receipt mechanism in this RFC; it will be handled via a scheduled mechanism in a separate effort.

## How a PosCreator experiences it

Nothing changes in how receipts are sent: the POS sends the same `ReceiptRequest` to the same sign endpoint. If the queue is configured for eInvoicing and/or eReporting, the returned `ReceiptResponse` simply contains additional entries in `ftSignatures` (and potentially additional data in `ftStateData`), the same way an SCU adds its signatures.

Which receipts are actually enriched depends on the concern:

- **eInvoicing** only applies to the invoice receipt cases (`B2C`, `B2B`, `B2G`). All other receipt cases pass through the eInvoicing service unchanged.
- **eReporting** is market-dependent: depending on the regulation it may act on daily operations (daily, monthly, or yearly closing), on specific document types, or on other receipt cases entirely. Which `ftReceiptCase`s a given eReporting service acts on is defined by that service/market.

Example: a queue in Greece configured with an eInvoicing service. The response to a `PointOfSaleReceipt` contains the myDATA signatures created by the SCU (invoice MARK, authentication code, QR URL) *plus* signatures added by the eInvoicing service, e.g.:

```json
{
  "ftSignatures": [
    { "Caption": "invoiceMark", "Data": "400001924190871", "...": "..." },
    { "Caption": "einvoice-id", "Data": "urn:peppol:...:5f9a...", "...": "..." },
    { "Caption": "einvoice-url", "Data": "https://einvoicing.example.com/invoices/5f9a...", "...": "..." }
  ]
}
```

## Configuration

The services are configured in the queue's configuration (the `Configuration` dictionary of the queue's `PackageConfiguration`), following the naming style of the existing `scu-timeout-ms` / `scu-max-retries` keys:

```json
{
  "einvoicing": {
    "endpoint": "https://einvoicing.example.com/v2",
    "timeout-ms": 15000,
    "max-retries": 1,
    "blocking": false
  },
  "ereporting": {
    "endpoint": "https://ereporting.example.com/v2",
    "timeout-ms": 15000,
    "max-retries": 1,
    "blocking": false
  }
}
```

- All configuration keys are lowercase (`einvoicing`, `ereporting`, `endpoint`, …), consistent with the existing lowercase/kebab-case queue configuration keys (`scu-timeout-ms`, `scu-max-retries`).
- Presence of a section enables the respective step; absence (the default) disables it. Each section supports exactly one endpoint.
- No authentication configuration is needed: every call implicitly carries the `cashboxid` and `accesstoken` headers, the same way signing requests are authenticated today.
- `blocking` controls what a *failure of the service* (unreachable, timeout, non-2xx) means for the receipt — see below. The default is `false`.

## Processing order and failure behavior

1. The receipt is processed as today: queue bookkeeping, country-specific command processor, SCU call.
2. If fiscalization **failed** (`ftState` signals an error), post-fiscalization processing is **skipped** — there is nothing valid to invoice or report.
3. If fiscalization succeeded, the queue calls the **eInvoicing** service first, then the **eReporting** service. Each call receives the *current* `ReceiptRequest`/`ReceiptResponse` — i.e. the eReporting service sees what the eInvoicing service added.
4. If a service call fails and `blocking` is `false` (default), the receipt is still returned successfully. The queue appends an informational failure signature so the POS (and support) can see that the step did not complete, e.g.:

```json
{ "Caption": "einvoicing-failed", "Data": "The configured eInvoicing service could not be reached (timeout after 15000ms).", "...": "..." }
```

5. If `blocking` is `true`, a failed service call marks the whole receipt as failed (`ftState` = error state), like an SCU failure. This is intended for markets/use cases where the eInvoice or the report is a legally required part of the receipt.

> ***Note:*** Because these steps run *after* fiscalization, a blocking failure means the SCU has already created a fiscal record for a receipt that the POS sees as failed. This is the same class of problem as an error occurring between SCU call and response today, and is the reason `blocking` defaults to `false`. See "Error and failure handling" in the reference-level explanation for the exact semantics.

## Latency

The calls are synchronous and happen inside the queue's sequential processing (one receipt at a time per queue). This is deliberate and not just an implementation shortcut: the results of eInvoicing and eReporting (signatures, state data) are part of the receipt handed back to the POS, so the queue must wait for them — deferred/asynchronous processing is not an option. A configured service adds its response time to every receipt; PosCreators should size `timeout-ms` accordingly.

# Reference-level explanation

## Interfaces

Following the SCU pattern (`fiskaltrust.ifPOS.v2.gr.IGRSSCD`, `fiskaltrust.ifPOS.v2.es.IESSSCD`), we add two market-agnostic interfaces to the `fiskaltrust.interface` package (namespace `fiskaltrust.ifPOS.v2`):

```cs
namespace fiskaltrust.ifPOS.v2;

public class ProcessRequest
{
    public required ReceiptRequest ReceiptRequest { get; set; }
    public required ReceiptResponse ReceiptResponse { get; set; }
}

public class ProcessResponse
{
    public required ReceiptResponse ReceiptResponse { get; set; }
}

public interface IEInvoicingService
{
    Task<ProcessResponse> ProcessReceiptAsync(ProcessRequest request);
}

public interface IEReportingService
{
    Task<ProcessResponse> ProcessReceiptAsync(ProcessRequest request);
}
```

- The `ProcessRequest`/`ProcessResponse` shape is deliberately identical to the market SCU contracts, but defined once in the market-agnostic `fiskaltrust.ifPOS.v2` namespace (the existing per-market `ProcessRequest`/`ProcessResponse` types remain untouched).
- Two distinct interfaces (rather than one shared) keep the two concerns separately addressable in DI/wiring and leave room for the contracts to diverge later (e.g. batch endpoints for eReporting) without a breaking change.
- This requires a new `fiskaltrust.interface` version (current reference: `1.3.78-rc1`).

### Contract for implementations

An implementation receives the full `ReceiptResponse` **including all fields generated by the Queue and the SCU** (`ftSignatures`, `ftState`, `ftStateData`, `ftReceiptIdentification`, `ftQueueItemID`, …) and returns the `ReceiptResponse` to be used from then on. Implementations:

- **may** append `SignatureItem`s to `ftSignatures`,
- **may** change `ftState` (e.g. set additional flags, or an error state if the service decides the receipt must fail),
- **may** add data to `ftStateData` — and **must merge** into the existing structure (`MiddlewareStateData`), never replace it,
- **must not** remove or alter existing signatures, and **must not** change identifying fields (`ftQueueItemID`, `ftQueueID`, `ftCashBoxID`, `cbReceiptReference`, `ftReceiptIdentification`, `ftReceiptMoment`),
- **must** be idempotent per `ftQueueItemID`: due to retries, the same `ProcessRequest` can arrive more than once and must not create a duplicate invoice/report,
- **must** decide relevance themselves: the queue forwards *every* successfully fiscalized receipt (including lifecycle, protocol, and zero receipts); a service that doesn't act on a given `ftReceiptCase` returns the response unchanged. For eInvoicing services this means acting only on the invoice receipt cases (`B2C`, `B2B`, `B2G`); for eReporting services the relevant receipt cases (e.g. daily operations such as daily/monthly/yearly closing, or specific document types) are defined per market.

The middleware treats the returned response as authoritative (same as with the SCU) but logs a warning and writes an action journal entry if a returned response dropped previously present signatures.

## HTTP wire protocol

Communication is strictly HTTP. The middleware ships one generic client used for both interfaces:

- `POST {endpoint}/processreceipt`
- Request body: the `ProcessRequest` serialized with `System.Text.Json` using the same options as the sign endpoint (`UnsafeRelaxedJsonEscaping`), `Content-Type: application/json`.
- Every request carries the `cashboxid` and `accesstoken` headers (the same implicit authentication used for signing requests); the receiving service authenticates the caller against these.
- Response `200 OK` with a `ProcessResponse` JSON body ⇒ success.
- Any other status code, a malformed body, or a timeout ⇒ **service failure** (handled per `blocking`, see below). There are no partial successes.
- Retries: up to `max-retries` additional attempts on timeout and 5xx (not on 4xx, which indicates a permanent problem with the request). Combined with the idempotency requirement above this is safe.

The client is created via the existing `IClientFactory<T>`/`ClientConfiguration` infrastructure (as `QueueESBootstrapper` does for `IESSSCD` today), with `UrlType = "rest"`; `grpc://` endpoints are rejected with a configuration error since this mechanism is HTTP-only by design.

## Configuration model

A new configuration class in `fiskaltrust.Middleware.Localization.v2`, parsed like `QueueESConfiguration`:

```cs
public class PostFiscalizationConfiguration
{
    [JsonProperty("einvoicing")]
    public PostFiscalizationServiceConfiguration? EInvoicing { get; set; }

    [JsonProperty("ereporting")]
    public PostFiscalizationServiceConfiguration? EReporting { get; set; }

    public static PostFiscalizationConfiguration FromMiddlewareConfiguration(MiddlewareConfiguration middlewareConfiguration)
        => JsonConvert.DeserializeObject<PostFiscalizationConfiguration>(JsonConvert.SerializeObject(middlewareConfiguration.Configuration));
}

public class PostFiscalizationServiceConfiguration
{
    [JsonProperty("endpoint")]
    public required string Endpoint { get; set; }

    [JsonProperty("timeout-ms")]
    public long? TimeoutMs { get; set; }              // default 15000

    [JsonProperty("max-retries")]
    public int? MaxRetries { get; set; }              // default 1

    [JsonProperty("blocking")]
    public bool Blocking { get; set; }                // default false
}
```

Validation at bootstrap: a present section with a missing/invalid `endpoint` fails queue startup with a clear error message — a half-configured compliance feature must not silently no-op.

## Insertion point in the pipeline

The step is implemented once, market-agnostically, in `SignProcessor` (`queue/src/fiskaltrust.Middleware.Localization.v2/SignProcessor.cs`) — *not* in the per-market command processors. It runs after the country processing returned (today line 101) and before the sandbox signature is appended and `FinishQueueItem` persists the response (today line 122). This guarantees the services see everything the Queue and SCU produced, and that everything they produce is persisted in `ftQueueItem.response` and returned to the POS.

```cs
(receiptResponse, countrySpecificActionJournals) = await ProcessAsync(receiptRequest, receiptResponse, queueItem).ConfigureAwait(false);
actionjournals.AddRange(countrySpecificActionJournals);

// NEW: post-fiscalization processing
var fiscalizationSucceeded = !receiptResponse.ftState.IsState(State.Error);
if (fiscalizationSucceeded)
{
    receiptResponse = await _postFiscalizationProcessor.ProcessAsync(receiptRequest, receiptResponse, queueItem, actionjournals).ConfigureAwait(false);
}
```

`PostFiscalizationProcessor` (new class in `fiskaltrust.Middleware.Localization.v2`) holds the two optional clients and encapsulates ordering and error handling:

```cs
public async Task<ReceiptResponse> ProcessAsync(ReceiptRequest request, ReceiptResponse response, ftQueueItem queueItem, List<ftActionJournal> actionJournals)
{
    response = await ProcessServiceAsync("einvoicing", _eInvoicingService, _configuration.EInvoicing, request, response, queueItem, actionJournals);
    response = await ProcessServiceAsync("ereporting", _eReportingService, _configuration.EReporting, request, response, queueItem, actionJournals);
    return response;
}
```

## Error and failure handling

Errors in this mechanism deserve their own section, because they have a property SCU errors don't have: **they occur after fiscalization**. When an SCU call fails, no fiscal record exists and the receipt as a whole fails. When an eInvoicing/eReporting call fails, the SCU has already created a fiscal record — the error handling must never pretend that record doesn't exist.

### Failure classes

1. **Fiscalization failed** (country processing/SCU returned an error state): post-fiscalization processing is skipped entirely. Unchanged behavior — action journal, no receipt journal, error response to the POS.
2. **Transport failure of a service**: endpoint unreachable, timeout, or 5xx after `max-retries`. Handled per the `blocking` setting (below).
3. **Protocol failure of a service**: 4xx response or a malformed/unparseable body. Never retried (the request won't get better); handled per the `blocking` setting.
4. **Service-signaled failure**: the service responds `200 OK` but deliberately returns a `ReceiptResponse` with an error `ftState`. This is the service exercising its contractual right (e.g. a market where the report is a mandatory part of the receipt) and is taken at face value, independent of `blocking`.
5. **Middleware-side bug**: any unexpected exception inside `PostFiscalizationProcessor` itself is caught and converted to the non-blocking handling below — a bug in a compliance add-on must never take down receipt processing.

### Handling

`ProcessServiceAsync` wraps each call in a `try`/`catch`; on failure (classes 2, 3, 5) it:

1. writes an `ftActionJournal` entry with the full technical details (exception, status code, attempt count),
2. appends a failure signature to the response (exact shape below),
3. if `blocking` is `true`, additionally calls `response.MarkAsFailed()`.

The failure signature is constructed the same way as the existing uncaught-exception signature in `SignProcessor`:

```cs
new SignatureItem
{
    ftSignatureFormat = SignatureFormat.Text,
    ftSignatureType = receiptRequest.ftReceiptCase.Reset().As<SignatureType>().WithCategory(SignatureTypeCategory.Failure),
    Caption = "einvoicing-failed", // or "ereporting-failed"
    Data = "<human-readable reason, e.g. 'The configured eInvoicing service could not be reached (timeout after 15000ms, 2 attempts).'>"
}
```

`Caption` is exactly `einvoicing-failed` / `ereporting-failed` (stable, machine-matchable). `Data` carries the human-readable reason only; the full technical details live in the action journal entry, which references the `ftQueueItemId`.

**Dropped-signature detection**: before handing the response to a service, the middleware snapshots the identities of the present `SignatureItem`s. If the returned response is missing any of them, the middleware logs a warning and writes an `ftActionJournal` entry listing the missing captions. The returned response is still used as-is (the contract makes the service authoritative, same as the SCU); the journal entry exists so a misbehaving service is diagnosable after the fact.

A failure of one service does not prevent the call to the next one (an unreachable eInvoicing service must not suppress legally required eReporting). All outcomes — including success — are persisted with the response in `ftQueueItem.response`, so the queue item is the audit trail for what was and wasn't invoiced/reported.

### Effect on fiscalization and the receipt journal

Today `SignProcessor` skips `InsertReceiptJournal` when `ftState` is an error state (lines 131–139), because an error means no fiscal receipt was created. With post-fiscalization processing this is no longer equivalent: a blocking service failure (or a service-signaled failure) happens *after* the SCU created a fiscal record, and that record **must** appear in the receipt journal.

Therefore the journal decision is based on the **fiscalization outcome**, captured before post-fiscalization processing runs (`fiscalizationSucceeded` above):

- fiscalization failed ⇒ action journal only, no receipt journal (unchanged behavior),
- fiscalization succeeded, post-fiscalization failed blocking (or service-signaled) ⇒ receipt journal **is** created; the persisted and returned response carries the error state and failure signature,
- fiscalization succeeded, post-fiscalization failed non-blocking ⇒ receipt journal is created; response stays successful with a failure signature appended.

### Recovery from the POS perspective

- **Non-blocking failure** (default): the POS receives a successful response and prints/issues the receipt as usual; the failure signature and action journal make the missed invoice/report visible for support and reconciliation. The middleware does not retry later — deferred delivery is not an option, since the results must be embedded in the receipt; handling the missed invoice/report is the service operator's or PosCreator's responsibility.
- **Blocking failure**: the POS receives an error response — but the underlying receipt **is** fiscalized and journaled. The POS **must not** simply re-send the receipt as a new transaction, since that would create a second fiscal record for the same sale. The correct recovery is the existing `ReceiptRequested` flag: it returns the persisted (failed) response for the original `cbReceiptReference` without reprocessing. Because of this sharp edge, `blocking` should only be enabled where regulation genuinely requires the eInvoice/report to be part of a valid receipt, and PosCreators enabling it must implement the `ReceiptRequested` recovery flow.
- **Ambiguous outcomes**: a timeout can occur *after* the service already acted. The middleware treats it as a failure; the service-side idempotency requirement (per `ftQueueItemID`) guarantees that a later retry — whether an automatic `max-retries` attempt or a manual re-submission — does not create a duplicate invoice/report.

## Interaction with existing behavior

- **Sequential processing**: the calls run inside `LocalQueueSynchronizationDecorator`'s single-threaded section, so a slow service directly throttles the queue. This is accepted for v1 (it is the same trade-off as a slow SCU) and is why timeouts are mandatory (default 15s, like the ES SCU default).
- **`ReceiptRequested` idempotency path**: replayed requests that find an existing queue item return the *persisted* response; post-fiscalization processing does not run again. Combined with the service-side idempotency requirement, a receipt is invoiced/reported at most once even across POS retries.
- **Sandbox**: the sandbox signature is appended after post-fiscalization processing, unchanged. `MiddlewareConfiguration.IsSandbox` is not forwarded specially — services see the sandbox flag in `ftState` like any other consumer.
- **Telemetry**: the existing `Activity` tags are extended with `queue.PostFiscalization.einvoicing` / `queue.PostFiscalization.ereporting` (`ok` / `failed` / `disabled`) so the effect on latency and error rates is observable.

## Wiring in the bootstrappers

Each v2 bootstrapper (`QueueESBootstrapper`, `QueueGRBootstrapper`, `QueuePTBootstrapper`) constructs the processor from configuration and passes it to `SignProcessor`:

```cs
var postFiscalizationConfiguration = PostFiscalizationConfiguration.FromMiddlewareConfiguration(middlewareConfiguration);
var postFiscalizationProcessor = new PostFiscalizationProcessor(
    loggerFactory.CreateLogger<PostFiscalizationProcessor>(),
    postFiscalizationConfiguration,
    eInvoicingClientFactory,   // IClientFactory<IEInvoicingService>
    eReportingClientFactory);  // IClientFactory<IEReportingService>

var signProcessor = new SignProcessor(loggerFactory.CreateLogger<SignProcessor>(), queueStorageProvider,
    signProcessorES.ProcessAsync, cashBoxIdentification, middlewareConfiguration, postFiscalizationProcessor);
```

When neither section is configured, `PostFiscalizationProcessor` is a no-op and `SignProcessor` behaves exactly as today (covered by existing tests). For tests, `InMemoryClientFactory<IEInvoicingService>` works the same way it does for `IESSSCD` today (`test/.../Helpers/ES/CashBoxBuilderES.cs`).

## Maintainability

The feature adds one seam in one shared class plus one new self-contained processor; market localizations don't change beyond constructor wiring. Because the contract is the same `ProcessRequest`/`ProcessResponse` shape developers already know from SCUs, reading a market's pipeline stays uniform: *validate → command processor (SCU) → post-fiscalization (eInvoicing, eReporting) → persist*.

# Drawbacks

- **Latency**: two additional synchronous HTTP calls in the sequential per-queue pipeline. A misconfigured or slow service degrades every receipt on that queue (bounded by the timeout).
- **No retry-later mechanism — by design**: because the eInvoicing/eReporting results are embedded in the receipt, the calls must complete synchronously; a background resend queue cannot fix a failed call after the response has been returned. A non-blocking failure therefore means the invoice/report for that receipt is *not* produced by the middleware, and recovery is the service operator's or the PosCreator's responsibility.
- **Interface package coupling**: requires a new `fiskaltrust.interface` release before the middleware change can be merged.
- **Response mutation from more actors**: the `ReceiptResponse` is now mutated by the Queue, the SCU, *and* up to two external services; misbehaving services can produce confusing responses. The contract rules plus the dropped-signature warning mitigate but don't prevent this.

# Rationale and alternatives

**Why this design:** it reuses the one extension pattern the ecosystem already understands (SCU-style `ProcessRequest`/`ProcessResponse`), it puts the hook in the single shared class of the v2 localization so every current and future v2 market gets it for free, and it is strictly additive and opt-in.

Alternatives considered:

- **Configure the services as additional `ftSignaturCreationDevices` packages in the cashbox configuration** (i.e. model them as SCU-like packages with their own `PackageConfiguration` and storage entities like `ftSignaturCreationUnitXX`). Rejected for now: these services are not signature creation devices, the storage/portal changes would be substantial, and the requirement is explicitly *queue-level* configuration of an HTTP endpoint. If the mechanism later needs versioned packages, rollout management, or multiple instances, this can be revisited (see future possibilities).
- **Extend the SCU contract to also cover eInvoicing/eReporting**. Rejected: the SCU's concern is fiscalization (including CTC transmission where that *is* the fiscalization, as in GR/ES); eInvoicing and eReporting are additional obligations on top of the fiscalized receipt, with their own opt-in configuration, failure semantics, and providers. Folding them into the SCU would mix the concerns and force every SCU to grow these capabilities.
- **Per-market hooks in the command processors** (each `ReceiptCommandProcessorXX` calls the services after `_sscd.ProcessReceiptAsync`). Rejected: N implementations of identical logic, and receipts handled outside the receipt command processor (invoice, protocol, daily operations) would need the same code again.
- **A generic webhook/plugin pipeline** ("call any list of URLs after signing"). Rejected: weaker contract, no typed response semantics, and invites uncontrolled response mutation. Naming the two concerns keeps the design reviewable and the portal UX explicit.
- **Doing nothing**: PosCreators integrate eInvoicing themselves, post-hoc, without the queue-generated fields and without a unified audit trail (action journals, persisted response). Each upcoming mandate would re-raise the question.

# Prior art

- The **SCU mechanism** itself is the primary prior art: a configured, interface-based, out-of-process component in the sign pipeline, with `ClientConfiguration`-based HTTP/gRPC transport, timeout and retry settings (`scu-timeout-ms`, `scu-max-retries`).
- **GR myDATA** and **ES VeriFactu** SCUs transmit data to the authority inline today. Note that this is *not* the eReporting concern of this RFC — it is CTC fiscalization, i.e. the transmission is what creates the fiscal proof, and it therefore correctly stays in the SCU. As prior art it demonstrates that synchronous authority communication inside the sign pipeline works operationally at receipt latency.
- **PT SAF-T** export via the `JournalProcessor` shows the asynchronous (scheduled/batch) flavor of eReporting; it is intentionally *not* covered by this per-receipt mechanism.

# Unresolved questions

To resolve during the RFC process:

- Whether dedicated `ftSignatureType` values should be reserved for post-fiscalization failure signatures instead of the generic `Failure` category.
- Whether the wire protocol needs a **version/capability handshake** (e.g. an `Echo`-style endpoint checked at startup) or whether a failing first call is acceptable.

Out of scope for this RFC (future, independent work):

- **Asynchronous reporting via a schedule**: batch/periodic obligations (e.g. SAF-T-style exports, monthly submissions) run at configured times over already-processed data, not per receipt — see "Synchronous vs. asynchronous reporting" in the guide-level explanation. This needs a scheduling mechanism and will be designed in a separate effort.
- Portal/configuration-UI support for editing the new configuration sections.

# Future possibilities

- **Onboarding IT and further markets to the v2 integration** automatically brings this mechanism to them — one of the stated goals of consolidating on the shared localization.
- **Multiple services per concern** (e.g. eReporting to more than one authority, or eInvoicing in more than one format) by turning each section into an array — deliberately excluded from v1 to keep ordering and failure semantics simple.
- **Packaged services**: if fiskaltrust ships first-party eInvoicing/eReporting services, the configuration could later be generated by the portal the same way SCU URLs are today, without changing the queue-side mechanism.
